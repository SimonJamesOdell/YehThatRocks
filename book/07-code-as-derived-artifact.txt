CHAPTER 7
Code as Derived Artifact
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

For the entire history of software engineering, source code has been the
canonical artifact. Everything else — build artifacts, test results,
documentation — was derived from the code. The code was the source of
truth. If the documentation disagreed with the code, the code was right.

In the directed AI paradigm, this hierarchy is inverted. The canonical
artifacts are the invariants and the observed behavior. The code is a
derived artifact — generated from the specification, verified by the
invariants, and regenerated when necessary.

This chapter explains the inversion and its implications.


The Traditional Hierarchy

In a traditional software project, the hierarchy of artifacts looks
like this:

1. Source code. The primary artifact. Written by developers. Reviewed
   by peers. Stored in version control. Everything else derives from it.

2. Tests. Derived from the code. Written to verify specific behaviors.
   Secondary to the code in authority — if a test fails, the test might
   be wrong.

3. Documentation. Derived from the code and the tests. Tertiary in
   authority. Often outdated. Rarely trusted.

4. Build artifacts. Derived from the code. Machine-generated.
   Disposable.

5. Observed behavior. Derived from the build artifacts. What the user
   actually experiences. The ultimate output, but the least
   authoritative — if the behavior is wrong, you fix the code, not
   the behavior.

This hierarchy made sense when humans wrote the code. The code was the
primary investment of labor. It was the thing that mattered. Everything
else was secondary.


The Inverted Hierarchy

In a directed AI project, the hierarchy is inverted:

1. Invariants. The primary artifact. They define what correctness means.
   They are the executable specification of the system's properties.
   They are the most authoritative artifact — if the code disagrees with
   an invariant, the code is wrong.

2. Observed behavior. Co-primary with invariants. What the system
   actually does when you interact with it. The ultimate verification.
   If the invariants pass but the behavior is wrong, the invariants
   have a gap.

3. Source code. A derived artifact. Generated by the AI from the
   specification. Verified by the invariants. Stored in version control
   for the AI's benefit, not the human's. Regenerated when the
   specification changes.

4. Build artifacts. Derived from the code. Machine-generated.
   Disposable. Same as in the traditional hierarchy.

5. Documentation. If the invariants are comprehensive, documentation
   is mostly redundant. The invariants are the documentation — they
   describe what the system does, and they are always current because
   they are executable.

The source code is no longer the source of truth. It is an intermediate
format between the invariants (what should be true) and the behavior
(what is true). It is the AI's private language for expressing
implementations. Humans do not need to read it. They need to read the
invariants and observe the behavior.


Regeneration, Not Maintenance

When code is a derived artifact, you do not maintain it. You regenerate
it.

If the invariants change — because you discovered a new category of
failure, or because the specification evolved — you direct the AI to
update the code so that the invariants pass. The old code is not
refactored. It is replaced.

If the code becomes too messy for the AI to work with — which is rare,
because the AI does not care about mess — you direct the AI to rewrite
the affected module. The rewrite is verified by the same invariants that
verified the original. If the invariants pass and the behavior is
correct, the rewrite is correct.

This is fundamentally different from traditional maintenance. In a
traditional project, refactoring is expensive because it risks
introducing bugs, and the only way to verify that you haven't broken
anything is to run the test suite and hope it covers the affected
paths. In a directed AI project, refactoring is cheap because the
invariants verify structural properties regardless of implementation.
If the invariants pass, the refactoring is safe.

The AI can rewrite a 3,000-line component in minutes. You verify the
result by running the invariants and checking the behavior. If
something is wrong, you argue with the AI until it's right. Total
cost: tens of minutes, not days or weeks.


The Implications for Code Review

If code is a derived artifact, code review is category error. You do
not review the output of a compiler. You review the input. If the input
(the invariants and the specification) is correct, and the output (the
observed behavior) matches the specification, the intermediate format
(the code) is correct by construction.

Traditional code review exists because traditional code is written by
humans, and humans make mistakes. The review catches those mistakes
before they reach production. But when the code is written by an AI
and verified by a growing portfolio of invariants, the review is
redundant. The invariants have already verified what the review would
check. And the invariants are more thorough, because they check
structural properties across the entire codebase, not surface-level
patterns in the specific lines that changed.

The skeptics who insist on reviewing AI-generated code are applying a
process designed for one paradigm to a system that operates under a
different paradigm. They are the equivalent of a DBA who insists on
inspecting ibdata1 files after every INSERT. The storage engine has
already verified the write. The SELECT has already confirmed the data.
The file inspection adds nothing but labor.


What Version Control Means

In a traditional project, version control is a history of human
decisions. Each commit represents a developer's choice about how to
implement something. The commit message explains the reasoning.

In a directed AI project, version control is a history of specification
changes. Each commit represents a change to what the system should do,
not how it does it. The commit message describes the behavior change,
not the implementation.

The code diff is not reviewed. It is generated, verified, and committed.
If a future session needs to understand why the code changed, the AI
reads the diff and the invariants — not the human, who never reads
diffs at all.

This may feel irresponsible if you have spent your career treating
version control as a communication tool between humans. But in this
paradigm, humans do not communicate through code. They communicate
through invariants and observed behavior. The code is the AI's domain.
Let the AI manage it.
