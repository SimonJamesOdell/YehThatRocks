CHAPTER 1
The Claim
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Code is dog food for the JIT compiler.

I mean this literally. The JavaScript engine that executes your web
application does not care whether your variable names are descriptive,
whether your functions are decomposed elegantly, or whether your
architecture follows clean-code principles. It cares about one thing:
can this be compiled to efficient machine code and executed?

Source code, in the runtime, is feedstock. It is consumed, transformed,
and discarded. The artifact that matters is the behavior of the running
system.

For decades, we have treated source code as something else entirely.
We have treated it as literature. We have developed aesthetic preferences
about it. We have held code reviews where senior engineers debate
naming conventions and function boundaries. We have built entire
methodologies — Clean Code, SOLID, Design Patterns — around the premise
that code should be beautiful, readable, and maintainable by humans.

This made sense when humans were the only readers. It made sense when the
primary cost of software was the labor of developers writing and
maintaining code by hand. It made sense when the only way to understand
what a system did was to read its source.

It no longer makes sense.


The Reader Has Changed

The primary reader of source code in my workflow is not a human. It is a
large language model — an AI that can ingest thousands of lines of code
in seconds, reason about their behavior, identify inconsistencies, and
propose changes. This reader does not care about aesthetics. It does not
get confused by inconsistent naming. It does not need functions to be
short or classes to have single responsibilities. It needs the code to be
correct, and it needs enough context to verify that correctness.

When the reader changes, the writing should change. You do not write a
letter to your friend the same way you write a legal contract. You do not
write documentation for end users the same way you write API reference
material. And you should not write code for an LLM the same way you write
code for a human colleague.

The LLM is a better reader than any human. It never gets tired. It never
skips a line because it looks boring. It never assumes that a function
named "getUser" probably does the right thing and moves on. It reads
everything, every time. It is the ideal audience for code — and that means
we can stop optimizing for the imperfect human audience we used to write
for.

This has a deeper implication: the codebase is not a storage format. It
is the AI's memory. When the AI needs to understand how a feature works,
it reads the relevant files. When it needs to modify behavior, it reads
the callers, the dependencies, and the invariants. The codebase is
retrieval-augmented generation — RAG — loaded on demand for whatever
purpose the session requires: inspection, explanation, modification,
analysis. You are not storing code in a repository. You are providing
persistent context for the AI's next session. The code is the memory. The
AI is the processor. You are the director.


The Database Analogy

Consider a MySQL database. When you issue an INSERT statement, the
database engine writes data to disk in its internal format — ibdata1
files, binary logs, index structures. As a database administrator, you do
not inspect these files after every write. You do not hold "storage format
reviews" where senior DBAs debate the byte alignment of InnoDB pages.

You trust the storage engine. You verify with SELECT statements. You
monitor replication lag and query performance. You only dive into raw
storage files when something breaks at a level the engine cannot explain.

The code in an AI-assisted project should be treated the same way. The
LLM is the storage engine. The source files are ibdata1. Your invariants
are the SELECT statements. Your QA session is the application-level smoke
test. You only inspect code directly when the verification surface has
failed and the AI cannot explain why.

This is not laziness. It is not recklessness. It is the same engineering
discipline that every DBA applies to their database — applied to the
entire codebase.

The analogy extends further than you might think. Before this project,
I had never heard of Prisma. The AI chose the ORM, designed the schema,
and generated the migrations. I did not review the SQL. I did not need
to know Prisma's query syntax. I verified that the API returned the
correct data and that the invariants passed. The tool is feedstock too,
not just the code. The LLM selects, configures, and operates the
toolchain. You direct, verify, and ship.

This is also the answer to one of the oldest frustrations in software
development: reusable code dies with its ecosystem. I was a Perl
programmer once. I built reusable libraries for authentication, session
management, and database access. When Perl declined and PHP rose, those
libraries became worthless — not because the code was bad, but because
the ecosystem had moved on. I rebuilt them in PHP. Then PHP declined
and JavaScript rose. I rebuilt them again. The pattern repeated across
frameworks, languages, and decades.

Reusable code is an investment in an asset that depreciates with its
platform. Reusable knowledge — the specification of what a system should
do, the invariants it must maintain, the architectural patterns it must
follow — is an investment in an asset that survives any platform. The
AI implements the specification in whatever stack is current. Next year,
when the stack changes, the specification remains valid. You direct the
AI to reimplement it. The code is ephemeral. The invariants are durable.

This is not a theory. It is what happened when I moved from PHP to
Node.js, and from Node.js to this project. The code was rewritten each
time. The knowledge of what the system should do survived.


The Exclusive Read/Write Lock

In my workflow, the LLM has an exclusive read/write lock over the source
code. I do not open files in an editor. I do not make manual edits. I do
not review pull requests by reading diffs. I describe what the system
should do, the AI generates the implementation, and I verify the behavior.

This is not a gimmick. It is a discipline. The moment I open a file and
start reading code, I have broken the paradigm. I have introduced a human
reader back into a system that was designed for a machine reader. I have
started forming opinions about code quality that are irrelevant to
correctness. I have substituted my aesthetic judgment for the system's
behavioral verification.

The no-peeking rule is the hardest part of this approach to maintain.
Every instinct from two decades of software development tells me to look
at the code. Every time something goes wrong, the first impulse is to
open the file and trace the logic. Resisting that impulse — and instead
describing the symptom to the AI and arguing with it until it finds the
root cause — is an act of will.

But it is necessary. Because the moment you look at the code, you start
trusting your eyes instead of your verification surface. And your eyes
are not as reliable as you think.


What This Chapter Argues

1. Source code is an intermediate representation between specification
   and behavior, not the canonical artifact of software development.

2. The primary reader of code in an AI-assisted workflow is the AI
   itself, and code should be optimized for that reader.

3. Treating code as the sole prerogative of the LLM — granting it an
   exclusive read/write lock — is not reckless. It is the same
   engineering discipline that database administrators apply every day.

4. The hardest part of this paradigm is not technical. It is
   psychological. It is resisting the instinct to read code, and
   trusting the verification surface instead.

The rest of this book explains how to build that verification surface,
how to direct the AI without reading its output, and what happens when
you commit to the paradigm fully.
