   0   11 + artifacts are the invariants and the observed behavior. The code is a
   0   12 + derived artifact — generated from the specification, verified by the

   0   14 +

   0   16 + 
   0   17 + 
   0   18 + The Traditional Hierarchy
   0   19 + 
   0   20 + In a traditional software project, the hierarchy of artifacts looks
   0   21 + like this:
   0   22 + 
   0   23 + 1. Source code. The primary artifact. Written by developers. Reviewed
   0   24 +    by peers. Stored in version control. Everything else derives from it.
   0   25 + 
   0   26 + 2. Tests. Derived from the code. Written to verify specific behaviors.
   0   27 +    Secondary to the code in authority — if a test fails, the test might
   0   28 +    be wrong.
   0   29 + 
   0   30 + 3. Documentation. Derived from the code and the tests. Tertiary in
   0   31 +    authority. Often outdated. Rarely trusted.
   0   32 + 
   0   33 + 4. Build artifacts. Derived from the code. Machine-generated.
   0   34 +    Disposable.
   0   35 + 
   0   36 + 5. Observed behavior. Derived from the build artifacts. What the user
   0   37 +    actually experiences. The ultimate output, but the least
   0   38 +    authoritative — if the behavior is wrong, you fix the code, not
   0   39 +    the behavior.
   0   40 + 
   0   41 + This hierarchy made sense when humans wrote the code. The code was the
   0   42 + primary investment of labor. It was the thing that mattered. Everything
   0   43 + else was secondary.
   0   44 + 
   0   45 +

   0   47 +

   0   49 + 
   0   50 + 1. Invariants. The primary artifact. They define what correctness means.
   0   51 +    They are the executable specification of the system's properties.
   0   52 +    They are the most authoritative artifact — if the code disagrees with
   0   53 +    an invariant, the code is wrong.
   0   54 +

   0   56 +    actually does when you interact with it. The ultimate verification.
   0   57 +    If the invariants pass but the behavior is wrong, the invariants
   0   58 +    have a gap.
   0   59 +

   0   61 +    specification. Verified by the invariants. Stored in version control
   0   62 +    for the AI's benefit, not the human's. Regenerated when the
   0   63 +    specification changes.
   0   64 + 
   0   65 + 4. Build artifacts. Derived from the code. Machine-generated.
   0   66 +    Disposable. Same as in the traditional hierarchy.

   0   70 +    describe what the system does, and they are always current because
   0   71 +    they are executable.

   0   93 + verified the original. If the invariants pass and the behavior is

   0   97 + traditional project, refactoring is expensive because it risks

   0    5 + This appendix describes the specific patterns of direction, argument,
   0    6 + and commissioning that produce working code from an LLM without reading
   0    7 + the output. These are not magic phrases. They are structural patterns
   0    8 + for directing AI analysis.
   0    9 + 
   0   10 + They are organized by the phase of the adversarial loop they apply to.
   0   11 + 
   0   12 + 
   0   13 + Pattern 1: Commissioning Features
   0   14 + 
   0   15 + When you want the AI to implement a new feature, describe:
   0   16 + 
   0   17 + - What the user should experience. Not what the code should do, but
   0   18 +   what the user should see and do. "When a user clicks the Watch Now
   0   19 +   button on a magazine article, the player should load the video
   0   20 +   associated with that article and begin playing."
   0   21 + 
   0   22 + - What should NOT happen. Negative constraints prevent the AI from
   0   23 +   making reasonable but wrong choices. "The player should not navigate
   0   24 +   away from the current context. The magazine page should remain
   0   25 +   visible behind the player."
   0   26 + 
   0   27 + - What invariants already apply. Reference existing patterns the AI
   0   28 +   should follow. "Use the same video resolution path that the shell
   0   29 +   layout uses for initial video loading."
   0   30 + 
   0   31 + - What to verify. "After implementing, the player should show the
   0   32 +   correct video, the magazine page should not reload, and the existing
   0   33 +   invariants should still pass."
   0   34 + 
   0   35 + Do not describe:
   0   36 + 
   0   37 + - How to implement it. Do not mention React hooks, state management,
   0   38 +   API calls, or component structure. The AI chooses the implementation.
   0   39 +   Your job is to define correct behavior.
   0   40 + 
   0   41 + - Edge cases you haven't observed. Only define constraints you know
   0   42 +   matter. If you define too many hypothetical constraints, the AI
   0   43 +   will over-engineer the implementation.
   0   44 + 
   0   45 + 
   0   46 + Pattern 2: Describing Symptoms
   0   47 + 
   0   48 + When something is wrong, describe:
   0   49 + 
   0   50 + - What you did. "I opened the magazine page and clicked Watch Now on
   0   51 +   the article about Metallica."
   0   52 + 
   0   53 + - What you expected. "I expected the player to load the Metallica
   0   54 +   video from that article."
   0   55 + 
   0   56 + - What actually happened. "The player loaded a different video. It
   0   57 +   seems to be a video I watched earlier in this session."
   0   58 + 
   0   59 + - When it happens. "It doesn't happen every time. It seems more
   0   60 +   likely when I reload the page first."
   0   61 + 
   0   62 + - What you've already checked. "The invariants pass. The magazine
   0   63 +   API returns the correct video ID. The problem is somewhere between
   0   64 +   the API response and the player loading."
   0   65 + 
   0   66 + Do not:
   0   67 + 
   0   68 + - Speculate about the cause. "I think the cache is stale" or "Maybe
   0   69 +   a race condition." Let the AI form the hypothesis. Your speculation
   0   70 +   will bias the AI toward confirming your guess rather than finding
   0   71 +   the actual cause.
   0   72 + 
   0   73 + - Describe code you peeked at. If you broke the no-peeking rule, do
   0   74 +   not mention it. Let the AI discover the code from scratch. Your
   0   75 +   peek might have shown you something irrelevant.
   0   76 + 
   0   77 + 
   0   78 + Pattern 3: Evaluating Explanations
   0   79 + 
   0   80 + When the AI proposes an explanation, evaluate it:
   0   81 + 
   0   82 + - Does it account for all observed behavior? If the explanation
   0   83 +   predicts the wrong video should load every time, but the symptom
   0   84 +   is intermittent, the explanation is wrong. "If the cache were
   0   85 +   stale, the wrong video would load consistently. But sometimes
   0   86 +   the correct video loads. Your explanation doesn't account for
   0   87 +   the intermittency."
   0   88 + 
   0   89 + - Is it specific enough? "The state was inconsistent" is not an
   0   90 +   explanation. "Which state? Inconsistent with what? When did it
   0   91 +   become inconsistent?" Demand specifics.
   0   92 + 
   0   93 + - Does it suggest a fix? A good explanation tells you what to
   0   94 +   change. "The SSR path made a playback decision that the client
   0   95 +   path was supposed to make, and the two paths disagreed." This
   0   96 +   suggests a specific fix: stop making playback decisions during SSR.
   0   97 + 
   0   98 + - Does it generalize? A good explanation identifies a class of
   0   99 +   failure, not a single instance. "This could happen in any route
   0  100 +   that renders during SSR and includes a component that triggers
   0  101 +   playback decisions." This suggests a class of fix: prevent
   0  102 +   playback decisions during SSR for all read-only routes.
   0  103 + 
   0  104 + 
   0  105 + Pattern 4: Arguing Productively
   0  106 + 
   0  107 + The adversarial stance is essential but must be productive:
   0  108 + 
   0  109 + - Challenge the explanation, not the AI. "That explanation doesn't
   0  110 +   account for why the symptom is intermittent." Not "You're wrong."
   0  111 + 
   0  112 + - Suggest alternative hypotheses only when you have evidence. "What
   0  113 +   if the timing of the SSR render matters? Could that explain the
   0  114 +   intermittency?" Not "Maybe it's something else entirely."
   0  115 + 
   0  116 + - Accept partial explanations. "The SSR path is probably involved,
   0  117 +   but why would it produce different results on different loads?"
   0  118 +   Build on what the AI got right while pushing for more.
   0  119 + 
   0  120 + - Recognize convergence. When the explanation accounts for all the
   0  121 +   evidence, accept it. Do not keep arguing for the sake of argument.
   0  122 +   "That explains the intermittency, the SSR path, and why the fix
   0  123 +   would prevent this in other routes. Let's implement that."
   0  124 + 
   0  125 + - Demand evidence. If the AI claims a certain function is the cause,
   0  126 +   ask how it determined that. "Did you trace the callers of that
   0  127 +   function? What path leads from the magazine page to the playback
   0  128 +   decision?" The AI should be able to describe the dependency chain.
   0  129 + 
   0  130 + 
   0  131 + Pattern 5: Commissioning Invariants
   0  132 + 
   0  133 + After a fix is implemented and verified, commission an invariant:
   0  134 + 
   0  135 + - Describe the class of failure, not the instance. "Any route that
   0  136 +   shouldn't make playback decisions must not make them during SSR."
   0  137 +   Not "The magazine page must not make playback decisions during SSR."
   0  138 + 
   0  139 + - Describe how to detect it. "Check that the getPlaybackDecision
   0  140 +   function is not called during server-side rendering for routes
   0  141 +   that don't need playback decisions."
   0  142 + 
   0  143 + - Define the scope. "This applies to all routes that don't pass
   0  144 +   a requestedVideoId parameter to the shell layout."
   0  145 + 
   0  146 + - Ask the AI to write the invariant script. "Write a verification
   0  147 +   script that asserts this property by reading the relevant source
   0  148 +   files and checking for the pattern."
   0  149 + 
   0  150 + - Verify the invariant catches the original failure. "Does this
   0  151 +   script fail if I revert the fix?" It should.
   0  152 + 
   0  153 + - Verify the invariant doesn't produce false positives. "Does this
   0  154 +   script pass on the current codebase?" It should.
   0  155 + 
   0  156 + 
   0  157 + Pattern 6: Commissioning Audits
   0  158 + 
   0  159 + Periodically, commission a structural audit:
   0  160 + 
   0  161 + - "Read every overlay route page and check whether it uses the
   0  162 +   OverlayHeader component. List any that don't."
   0  163 + 
   0  164 + - "Read every API route handler and check whether mutation methods
   0  165 +   (POST, PATCH, DELETE, PUT) call verifySameOrigin. List any that
   0  166 +   don't."
   0  167 + 
   0  168 + - "Read every component that fetches data and check whether it uses
   0  169 +   AbortController for cleanup. List any that don't."
   0  170 + 
   0  171 + - "Read the entire scripts/ directory and identify duplicated
   0  172 +   patterns. Propose a shared library that eliminates the duplication."
   0  173 + 
   0  174 + These audits are the equivalent of CODE_SMELLS.md. They are
   0  175 + commissioned on demand, not run automatically. They find systemic
   0  176 + issues that individual invariants might miss. After the audit,
   0  177 + commission invariants that prevent the issues from recurring.
   0  178 + 
   0  179 + 
   0  180 + These patterns are not a complete taxonomy. They are what worked for
   0  181 + one project. Your project will develop its own patterns. The common
   0  182 + thread is structural, not linguistic: describe what should happen,
   0  183 + observe what actually happens, argue about the gap, and commission
   0  184 + permanent guarantees.
